# Planet Busters Ver2 実装計画

- 作成日: 2026-10-31
- 状態: 提案・未着手。数値や画面仕様は各フェーズ着手時に確定する。
- 対象: Ver1 の CPU 対戦を拡張し、繰り返し遊べるゲームと招待制の人対人対戦を提供する。
- 関連資料: [Ver1 仕様・実装計画](strategy-space-battle-spec-and-plan.md)、[Ver1 検証記録](phase5-release-verification.md)

## 1. 目標と対象範囲

Ver2 は単一の大型リリースではなく、既存の対局を維持しながら段階的にリリースする。前回提案した「Ver2 以降」の候補も、以下の全体計画に含める。

| 対象 | 成果 | 主なフェーズ |
| --- | --- | --- |
| 複数マップ | 選択できる固定マップを既存の1種類から計3種類にする | 2 |
| CPU 難易度 | 初級・標準・上級を選択できる | 3 |
| 戦況・攻撃情報 | 攻撃前の予測と行動結果を分かりやすく表示する | 1 |
| 戦績・対局履歴 | マップ・難易度などの条件で過去対局を振り返る | 4 |
| 新ユニット | 役割の異なる長射程の支援艦を1種類追加する | 5 |
| チュートリアル | ゲームの基本を短い実戦形式で学べる | 5 |
| バランス検証 | 先手・配置・マップ・難易度を分けて検証する | 0〜8 |
| ブラウザ自動テスト | 主要フローと異常系を継続的に検証する | 0〜8 |
| リプレイ | 対局を読み取り専用で振り返る | 6 |
| 対人戦 | 招待制の非同期ターン制対戦を提供する | 7 |
| 編成・初期配置 | 対局開始前に制約内で自軍を選択・配置する | 8 |

ランダムマップ、自動マッチング、ランク、観戦、チャット、課金、育成・装備は今回の対象外とする。WebSocket やプッシュ通知も必須とはせず、まずは画面表示中のポーリングで同期する。これらを将来追加できるようには配慮する。

## 2. 現状と設計上の前提

- 対局は CPU 戦のみで、固定マップ「星雲の交差点」、戦艦・戦闘機、各ユニット1ターン1行動が基本。CPU は決定的な優先順位で行動する。
- ドメインロジックは `packages/api/src/game/`、API は `packages/api/src/routers/game.ts`、永続化は `packages/db/src/schema/game.ts`、表示は `apps/web/src/components/game/` と認証配下のルートにある。DB の状態を正本とし、対局の版数で競合を検出する。
- 現行の陣営名 `human` / `cpu`、手番処理、対局の所有者確認、画面操作は CPU 戦を前提とする。対人戦では単なるモード追加ではなく、陣営と操作者を分離して認可・表示・ターン処理を見直す。
- 行動履歴には攻撃結果などが保存されるが、現行の直近履歴表示は最大10件であり、全履歴の安定した順序やルール変更後の完全な再生は保証されない。履歴があるだけで過去対局をすべてリプレイできるとは扱わない。
- 検証記録では同じ CPU 同士の1,000対局で先手配置の勝率は65.7%。先手と配置の影響は分離できておらず、人間対 CPU の公平性を直接示す数値でもない。
- ユーザーによる Ver1 の一通りのプレイ確認は実施済み。自動化されたブラウザ E2E や通信失敗などの全受け入れ条件の網羅は別途確認する。

## 3. 共通設計・互換性

### 3.1 対局ごとのルール固定

- 新規対局にルール・マップ定義のバージョンを記録し、対局中にバランス値や定義を更新しても開始時のルールで再開・再生する。マップとルールはバージョン付き定義を保持する方式を基本とし、定義削除時の扱いも実装時に確認する。
- 既存対局は Ver1 のルールと既存マップへ明示的に対応付ける。既存の進行中対局は Ver1 の編成・能力・CPU 判断で完了できるようにする。既存 API の省略可能パラメーターには従来相当の既定値を設ける。
- 難易度、編成、配置、対局開始時状態など、再開・履歴・リプレイに必要な設定は対局単位で永続化する。乱数結果はサーバーで確定し、クライアントの予測結果を正本にしない。
- マイグレーションは Drizzle の生成機能を使い、空 DB と Ver1 のデータを持つ DB の両方で検証する。バックアップ・復旧手順を用意し、既存データを破壊する変更は避ける。ビルド済みサーバーの起動時マイグレーションと静的配信も維持する。

### 3.2 操作と認可

- ルール判定・攻撃予測は可能な限り共通のドメイン関数を使用し、表示とサーバーの計算差を防ぐ。実行時はサーバーが認証、参加者、手番、合法手、期待版数を再検証する。
- 対局更新・履歴追加・版数更新を一貫したトランザクションで扱う。競合や通信失敗時は最新状態を再取得し、重複適用を防ぐ。
- UI は狭い画面、キーボード、色覚への配慮、動きの軽減設定を継続して満たす。演出失敗時にも対局を続行できることを維持する。

## 4. 実装フェーズ

工数は相対評価（小・中・大）であり、日数の見積もりではない。フェーズごとに実装・テスト・レビューを完了し、必要なら個別にリリースする。

### フェーズ 0: 品質基盤と互換性の確立（大）

**作業**

1. Ver1 の仕様、既存対局、DB マイグレーション、ルール・マップ定義の固定方法を調査し、新旧対局の互換性テスト用データを準備する。ルールのバージョン解決と Ver1 の既定値を導入する。
2. ブラウザ E2E 基盤を導入し、登録・ログイン、新規開始、移動・攻撃、ターン終了、再読み込み・再開、降参、勝敗を自動化する。テスト用 DB と認証データを分離し、乱数や勝敗は制御可能なテスト条件で再現する。
3. 競合、通信遮断・復帰、ポップアップ拒否、狭い画面も検証する。CI で再現可能なテストを実行し、環境上難しい項目は手動手順と理由を記録する。
4. シミュレーターを先手と配置の組み合わせを入れ替えられるよう拡張し、勝率・対局長・未完了・到達不能を記録する。閾値を決める前に結果と実プレイの感想を収集する。

**完了条件:** Ver1 データの移行後に既存対局を再開・終了できる。主要 E2E と異常系が CI または明記された手順で検証され、先手と配置を分けた基準値が記録される。

### フェーズ 1: 戦況・攻撃情報の改善（中）

**作業**

- 対象を選択した攻撃確認画面に、命中率、ミス・通常・クリティカルの確率、各結果のダメージと対象の現在 HP／結果別残 HP を表示する。予測値であり確定結果ではないことを明示する。
- CPU を含む直近行動について、移動元・移動先、攻撃対象、結果、ダメージを追いやすくする。必要な情報が不足する場合は新規履歴の記録内容を拡張し、古い履歴は表示可能な範囲にフォールバックする。
- 送信中・CPU 処理中・競合後の状態表示と操作可否を整理し、攻撃演出およびポップアップ代替を維持する。

**テスト・完了条件:** 予測値と実際のルールの境界値が一致し、結果を事前確定しない。CPU 行動と攻撃結果を追跡でき、競合・再読み込み・演出失敗後も整合する。

### フェーズ 2: 固定マップの追加（中）

**作業**

- 既存マップに加え、障害物と通路の異なる固定マップを2種類追加し、対局開始画面で名称・特徴・プレビューを表示して選択可能にする。既存マップを既定とする。
- 定義の範囲外・重複・初期配置を検証し、両陣営から敵惑星へ攻撃できる位置への到達可能性を確認する。マップ定義のバージョンを固定し、再開時も同じ地形を使う。
- 各マップで先手・配置を入れ替えたシミュレーションと実プレイを行い、勝率と到達不能・長期化を評価する。

**テスト・完了条件:** 3マップすべてを選択・開始・再開・完了でき、無効なマップ指定を拒否する。マップ検証とシミュレーションを CI に追加する。

### フェーズ 3: CPU 難易度（中〜大）

**作業**

- 対局開始時に初級・標準・上級を選択し、設定を対局と履歴に保存する。標準は現行 CPU 相当を基準とし、既存対局の挙動も維持する。
- 初級は意図的に単純な判断、上級は被弾リスク・撃破期待値・主惑星防衛・味方の位置を考慮する。能力値を変更せず判断の違いを基本とし、必要な乱択は注入可能な乱数でテストする。
- 判断時間に上限を設け、サーバー側の CPU ターン処理と競合復旧を維持する。難易度とマップ別にシミュレーション・人間の試遊を行う。

**テスト・完了条件:** 各難易度で合法手のみを選び、同一条件で判断を再現できる。設定が再開後も維持され、難易度の体感差と極端な偏りを試遊結果で確認する。勝率目標は試遊後に設定する。

### フェーズ 4: 戦績と履歴（中）

**作業**

- 対局一覧にマップ、難易度、勝敗、終了理由、開始・終了日時、ターン数を表示する。完了対局の経過時間は開始から終了までの壁時計時間と明記し、プレイ時間とは区別する。
- 自分の対局を対象に、マップ・難易度別の対局数・勝敗・勝率を集計し、条件による絞り込みとページネーションを提供する。降参を敗北として扱い、中断・未完了は勝率の分母に含めない。
- 旧対局の難易度など不明な情報は `Ver1 / 不明` と表示し、推測値で集計しない。対人戦の相手やモードもフェーズ7で追加する。

**テスト・完了条件:** 空履歴、旧データ、降参、複数ページ、他ユーザーのアクセス拒否を検証し、表示件数・勝率が保存済み対局と一致する。

### フェーズ 5: 新ユニットとチュートリアル（大）

**作業**

- 長射程・低機動の支援艦を1種類追加する。HP・射程・攻撃力・命中補正・初期配置は試遊とシミュレーションで決め、既存2種と明確に役割を分ける。射線などの基本ルールは維持する。
- Ver2 の新規対局における初期編成を定め、マップ検証、CPU の選択・評価、描画、名称、攻撃予測、履歴とルール表を新種別に対応させる。旧対局の編成・能力は変更しない。
- 独立した練習用シナリオで、選択、移動、射線、攻撃予測、攻撃結果、手番終了、勝利条件を順に説明する。通常の戦績には含めず、スキップ・再実行を可能にする。

**テスト・完了条件:** 新ユニットの移動・射線・攻撃・破壊・CPU 操作を検証し、全対象マップで対局を完了できる。チュートリアルを完了・途中終了・再開でき、通常対局や戦績を汚染しない。

### フェーズ 6: リプレイ（大）

**作業**

- 新規対局について、初期状態、ルール・マップのバージョン、全行動、攻撃乱数と確定結果、ターン移行・降参を再生可能な形式で記録する。マッチ内の単調増加する行動順序を付与し、同一時刻の行動も安定して並べる。
- 認可済み参加者向けにページング可能な読み取り専用 API と画面を作り、開始・一時停止・1手送り・速度変更・任意位置への移動を提供する。再生は対局の正本を更新しない。
- Ver1 履歴について初期状態・行動順・自動ターン移行などを監査する。完全かつ一意に復元できる場合のみ対応し、保証できない対局はリプレイ不可と明示して通常履歴を表示する。欠落を推測で補って完全再生と表示しない。

**テスト・完了条件:** 移動、攻撃3結果、撃破、ターン自動終了、降参、勝敗を含む対局で最終状態が保存済み状態と一致する。順序重複、履歴不足、旧ルール、非参加者のアクセス、再生中の状態非変更を検証する。

### フェーズ 7: 招待制の非同期対人戦（大）

**作業**

- ログインユーザーが招待を作成し、別ユーザーが参加して開始する。招待の失効・取り消し、自己参加・二重参加の拒否を定める。推測困難な招待トークンを用い、認証・参加権限を確認する。
- 陣営を操作主体から分離し、両参加者が自分の陣営として閲覧・操作できるよう、ドメイン型・DB・API・UI・履歴を対応させる。既存の `human` / `cpu` 値をどう移行・互換表示するかは実装前に確定する。
- 各手番はサーバーで検証し、同時操作は版数と原子的更新で競合検出する。手番中でない参加者の操作を拒否し、双方の降参・切断・再接続を扱う。
- ダッシュボードと対局画面で自分の手番を表示し、画面表示中のポーリングと再取得で相手の行動を反映する。ブラウザを閉じた状態への通知は提供しない。放置対局の自動敗北・時間制限は設けず、参加者は降参できる。

**テスト・完了条件:** 2アカウントで招待から勝敗・再開まで対局できる。第三者の閲覧・操作、招待の不正利用、同時送信、二重参加、競合、切断・復帰を自動検証する。CPU 戦と旧対局にも回帰がない。

### フェーズ 8: 編成・初期配置（大）

**作業**

- 3種類のユニットから、総コスト・機数上限に従って編成し、各マップの自陣配置範囲に配置する画面を追加する。初期案は各陣営同一予算・同一制約とし、具体的なコスト・上下限は実装前のバランス検証で確定する。
- 範囲外、重複、障害物・惑星との重なり、予算超過、配置不足、勝利不能な編成をサーバーで拒否する。既定編成と自動配置も用意する。CPU 戦の CPU 側には検証済み編成を用意する。
- 対人戦では両者が独立して編成・確定し、両者の確定後に開始する。確定前の相手編成・配置は API に返さず、開始後に公開する。再読み込み時も自分の準備状態を復元できるようにする。
- 対局開始時の編成・配置を保存し、再開・戦績・リプレイに反映する。多数の組み合わせをシミュレーションし、不利な配置や長期化を検出する。

**テスト・完了条件:** CPU 戦・対人戦で有効な編成を選んで開始・再開・完了でき、不正入力と未確定情報の漏えいを拒否する。開始時状態からリプレイが一致し、既定編成でも開始できる。

## 5. 依存関係とリリース順

```text
0 品質・互換性
 └→ 1 戦況表示 → 2 マップ → 3 CPU難易度 → 4 戦績
                                               └→ 5 新ユニット・チュートリアル
                                                    └→ 6 リプレイ
                                                         └→ 7 対人戦
                                                              └→ 8 編成・初期配置
```

この順序を基本とする。特にルール固定はマップ・ユニット変更に先行し、リプレイは後続の対人戦・自由編成の開始状態も扱えるよう設計する。フェーズ1〜4で CPU 戦の遊びやすさを先行提供し、フェーズ5以降は規模とリスクを確認しながら順次提供する。

## 6. 横断的な検証・リリース基準

各フェーズで以下を実施する。

1. **ユニットテスト:** 追加ルール・境界値・不正操作・乱数の再現性を検証する。
2. **API・DB 結合テスト:** 認証・認可、入力検証、原子性、楽観的排他、既存 DB の移行、再開を検証する。
3. **UI・ブラウザ E2E:** 追加した主操作とエラー復帰を確認し、主要な既存フローを回帰テストする。狭い画面、キーボード、演出無効・ポップアップ拒否も対象とする。
4. **バランス:** 固定シードでマップ・先手・配置・CPU 難易度を分けて集計し、到達不能・異常終了・長期化の有無を確認する。勝率には対局数と前提を併記し、実プレイの結果も合わせて判断する。過去値との比較条件を記録する。
5. **品質ゲート:** 既存の Biome lint、型検査、Bun テスト、シミュレーションに加え、導入した E2E とビルドを実行する。ビルド済みサーバーでの静的配信・マイグレーションを確認する。
6. **リリース:** 既存対局の互換性、DB のバックアップ・復旧、既知の制約と手動検証結果を記録する。重大な未解決不具合やデータ破壊がある状態では公開しない。

## 7. 着手前に確定する事項

- **バランス:** 各新マップの配置、新ユニット能力、難易度の評価基準、編成コストは試作と試遊で決める。シミュレーション勝率のみを公平性の保証としない。
- **旧対局:** Ver1 の進行中対局は旧ルールで継続する。旧履歴の完全リプレイ可否は実データを監査して決める。
- **対人戦:** 招待の有効期間、ポーリング間隔、対局開始時の先手決定方法、招待や準備中の取り消し操作はフェーズ7の詳細設計で確定する。
- **準備画面:** 対人戦の準備中に片方が確定を解除できる条件、招待失効時の下書き保持期間はフェーズ8の詳細設計で確定する。
- **配信範囲:** 対人戦の画面外通知、自動マッチング、ランキングは本計画に含めない。必要になった場合は追加仕様として扱う。
