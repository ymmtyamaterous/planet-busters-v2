# 戦略スペースバトル 詳細仕様・実装計画書

- 対象プロジェクト: Planet Busters (Web)
- 作成日: 2026-09-23
- 原案: `docs/user/draft.md`
- 対象リリース: CPU 対戦の最小実用版（MVP）

## 1. 目的とスコープ

プレイヤーが自軍の主惑星を防衛しつつ、艦隊を運用して敵の主惑星を撃破する、1 対 1 のターン制宇宙戦略ゲームを実装する。

### 1.1 MVP に含めるもの

- ログイン済みユーザーと CPU による 1 対 1 の対戦
- 固定サイズのマップ、障害物となる小惑星、両軍の主惑星
- 戦艦・戦闘機の配置、移動、攻撃、ターン進行
- 命中 / ミス / クリティカルを含む攻撃判定
- ユニット種別ごとの対対象命中補正
- 攻撃結果を表示する独立した演出画面（ポップアップ不可時の代替表示を含む）
- 対局の保存、再開、履歴閲覧

### 1.2 MVP では扱わないもの

- 人間同士のマッチメイキング・リアルタイム同期
- 複数マップ、ランク、観戦、チャット、課金要素
- ユニットの編成・育成・装備・資源採掘
- 小惑星の破壊、建築、地形変化
- 同時ターン制および制限時間切れの自動処理

これらは MVP のゲーム状態・アクション履歴を再利用して後続リリースで追加する。

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| マッチ | 1 回の対局全体。開始から勝敗確定までを表す。 |
| 陣営 | 人間または CPU が操作する一方の軍。 |
| 主惑星 | 各陣営が 1 つ持つ拠点。HP が 0 になるとその陣営は敗北する。 |
| ユニット | マップ上で行動する戦艦または戦闘機。 |
| 行動 | 1 ユニットが 1 ターンに実行する移動または攻撃。 |
| ターン | 片方の陣営が行動できるフェーズ。プレイヤーと CPU が交互に進行する。 |
| マップ座標 | 左上を `(0, 0)` とする整数グリッド座標。`x` は右方向、`y` は下方向に増える。 |

## 3. ゲームルール仕様

### 3.1 対局の初期状態

- マップは `12 × 8` グリッドとする。
- 人間陣営は左側、CPU 陣営は右側に初期配置する。
- 各陣営は主惑星 1 基、戦艦 2 隻、戦闘機 3 機を持つ。
- 小惑星はマップごとに固定レイアウトを採用し、両軍が到達可能な複数経路を残す。
- 小惑星、主惑星、ユニットは同一マスに重ならない。
- 対局開始時は人間陣営のターンとする。

固定レイアウトはゲームルールのテストとバランス調整を安定させるために採用する。将来、乱数シードとマップ定義をマッチに保存することでランダム生成へ拡張できる。

### 3.2 ターンと行動

1. ターン開始時に、その陣営に属する生存ユニットの `hasActed` を `false` にする。
2. 操作側は未行動の各ユニットに対して、**移動**、**攻撃**、または**待機**を 1 回選択できる。
3. 行動済みユニットの `hasActed` を `true` にする。
4. 全生存ユニットが行動済みになるか、操作側が「ターン終了」を選ぶとターンを終了する。
5. 主惑星の HP が 0 以下なら即座にマッチを終了し、残りの行動は実行しない。
6. 人間ターン終了後、CPU は同じルールで行動し、その後に人間ターンへ戻す。

MVP では 1 ユニットにつき 1 ターン 1 行動とし、移動後の攻撃や攻撃後の移動は許可しない。待機は明示的な行動として履歴に残す。

### 3.3 移動ルール

- 移動先はユニットの移動力以内にある空きマスに限る。
- 移動距離は上下左右への移動回数（マンハッタン距離）で算出する。
- 小惑星、主惑星、他ユニットのマスは通過・停止できない。
- 斜め移動は MVP では許可しない。
- 経路が障害物で塞がれている場合、距離内であっても移動できない。
- 移動候補はクライアントで表示するが、最終的な経路・移動可否はサーバーで検証する。

### 3.4 攻撃ルール

- 攻撃対象は攻撃側ユニットの攻撃範囲内にある、敵ユニットまたは敵主惑星とする。
- 攻撃距離はマンハッタン距離で判定する。
- 攻撃は小惑星を越えて実行できない。攻撃側と対象を結ぶ水平・垂直の直線上に小惑星がある場合は射線が遮られる。
- MVP の攻撃は同一行・同一列の射撃に限定する。斜め・曲射・範囲攻撃は将来拡張とする。
- 攻撃結果は `miss`、`hit`、`critical` のいずれかとする。`critical` は必ず命中する。
- HP が 0 以下になったユニットは直ちにマップから除去し、以後の操作対象にできない。

### 3.5 ユニットと主惑星の初期パラメーター

数値は初期バランス値であり、対戦ログとテスト結果に基づいて調整する。

| 種別 | HP | 移動力 | 射程 | 基礎攻撃力 | 戦闘機への命中補正 | 戦艦への命中補正 | 惑星への命中補正 | 役割 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 戦艦 | 12 | 2 | 4 | 4 | -10 | +5 | +10 | 高耐久の惑星攻撃役 |
| 戦闘機 | 5 | 4 | 2 | 2 | +20 | 0 | -15 | 機動・迎撃役 |
| 主惑星 | 30 | 0 | 0 | 0 | — | — | — | 勝敗条件となる拠点 |

### 3.6 命中・ダメージ計算

攻撃結果は、サーバー側で生成した乱数により決定する。クライアントで乱数を生成してはならない。

1. 基本命中率を `70` とする。
2. 攻撃側種別と防御側種別に対応する命中補正を加える。
3. 最終命中率は `20` から `95` の範囲に丸める。
4. `0..99` の乱数を 1 回生成し、結果を以下で決定する。

$$
P_{critical}=10,\quad
P_{hit}=\max(0, P_{accuracy}-10),\quad
P_{miss}=100-P_{accuracy}
$$

- 乱数が `0..9`: `critical`
- 乱数が `10..(accuracy - 1)`: `hit`
- それ以外: `miss`

ダメージは次式で計算する。

$$
Damage =
\begin{cases}
0 & \text{結果が miss}\\
Attack & \text{結果が hit}\\
Attack \times 2 & \text{結果が critical}
\end{cases}
$$

実装時には、テストで結果を再現できるよう、乱数生成器をゲームエンジンへ依存性注入する。

### 3.7 勝敗・中断

- 相手主惑星の HP を 0 以下にした陣営が勝利する。
- 勝者、敗者、終了理由、終了日時をマッチに保存する。
- MVP では任意の降参を提供する。降参した陣営は敗北する。
- 対局中に画面を閉じても、サーバーに保存済みの状態から再開できる。
- CPU の処理中に通信が切れた場合も、CPU ターンはサーバー側で最後まで確定させる。

## 4. CPU 仕様

CPU は毎ターン、未行動ユニットを順番に処理する決定的な優先順位ロジックを使用する。

1. 射程内で主惑星を攻撃できる場合、主惑星を攻撃する。
2. 射程内で撃破可能な敵ユニットがいる場合、最も HP が低い対象を攻撃する。
3. 射程内の敵ユニットを攻撃する。
4. 攻撃可能な位置へ移動できる場合、その中で敵主惑星への距離が最も短くなる位置へ移動する。
5. それ以外は敵主惑星に近づく有効経路上を移動する。
6. 合法手がない場合は待機する。

同点時は座標順、ユニット ID 順で選択する。MVP では CPU 行動のランダム性を持たせず、テスト可能性を優先する。

## 5. 画面・UX 仕様

### 5.1 画面一覧

| 画面 | 認証 | 主な機能 |
| --- | --- | --- |
| ダッシュボード | 必須 | 新規 CPU 戦開始、進行中対局の再開、対局履歴の表示 |
| 対局画面 | 必須 | マップ表示、ユニット選択、移動・攻撃・待機、ターン終了 |
| 攻撃演出画面 | 必須 | 攻撃開始から結果・ダメージまでのアニメーション表示 |
| 結果ダイアログ | 必須 | 勝敗、終了理由、ダッシュボードへ戻る導線 |

### 5.2 対局画面

- Phaser のキャンバスでグリッド、地形、惑星、ユニットを描画する。
- React の UI オーバーレイで現在ターン、主惑星 HP、選択ユニット情報、操作ボタンを表示する。
- 自軍ユニットを選択すると、移動可能マスを青、攻撃可能な敵を赤で強調する。
- 選択中のユニットに対し、`移動`、`攻撃`、`待機`の実行可能な操作のみを活性化する。
- 敵ターン中は操作を無効化し、「CPU が行動中」を表示する。
- 直近の行動ログを最大 10 件表示する。
- 画面幅が狭い場合、情報パネルをキャンバス下部に縦積みし、マップは横スクロール可能にする。

### 5.3 攻撃演出画面

攻撃ボタンのクリックはユーザー操作として扱い、その同期処理内で専用の小ウィンドウを開く。攻撃結果の確定後、その画面へ `postMessage` で演出データを送信する。

- 表示内容: 攻撃側・防御側、結果、ダメージ、残り HP。
- 演出: 発射、着弾、結果表示の順に再生する。
- `miss`: 弾道が対象の横を通過し、`MISS` を表示する。
- `hit`: 通常の着弾・爆発とダメージ数値を表示する。
- `critical`: 拡大された爆発、画面シェイク、`CRITICAL` を表示する。
- 演出完了またはスキップ後、対局画面の状態を再取得して操作を再開する。
- ブラウザがポップアップを拒否した場合、同一デザインのモーダル演出に自動フォールバックする。
- 演出画面はゲーム状態を変更しない。正本となる状態変更はサーバーの攻撃アクション処理のみが行う。

### 5.4 アクセシビリティ

- 操作ボタンにテキストラベルと `aria-label` を付与する。
- 色だけに依存せず、選択・移動・攻撃可能状態をアイコンまたはパターンでも区別する。
- 攻撃演出には「スキップ」ボタンを用意し、アニメーションを無効化する OS 設定を尊重する。
- キーボードでユニット選択、移動候補選択、ターン終了を実行可能にする。

## 6. システム設計

### 6.1 責務分離

| 層 | 責務 | 配置候補 |
| --- | --- | --- |
| ドメイン層 | マップ検証、移動、射線、攻撃、勝敗、CPU 判断。UI・DB に依存しない。 | `packages/api/src/game/` |
| API 層 | 認証、入力検証、トランザクション、永続化、ドメイン層呼び出し。 | `packages/api/src/routers/game.ts` |
| 永続化層 | Drizzle スキーマ、リポジトリ、マイグレーション。 | `packages/db/src/schema/game.ts` |
| 表示層 | Phaser 描画、React 操作 UI、状態の取得と同期。 | `apps/web/src/components/game/`、`apps/web/src/routes/_auth/game.$matchId.tsx` |

ゲームルールは Phaser シーンや ORPC ハンドラへ直接記述しない。これにより、CPU・API・テストが同一の判定ロジックを使用できる。

### 6.2 状態の正本と更新方式

- 正本は DB に保存したマッチ、ユニット、アクション履歴とする。
- クライアントは `getMatch` で状態を取得し、アクション成功後に返却された最新状態で置き換える。
- `submitAction` は `matchId`、`expectedVersion`、アクション内容を受け取る。
- サーバーは更新時に `expectedVersion` を検証し、成功時に `version` を 1 増加させる。
- バージョン不一致時は競合エラーを返し、クライアントは状態を再取得して再操作を促す。
- CPU の一連の行動は、人間のターン終了処理と同一トランザクション内、または人間操作が受け付けられない `cpu_turn` 状態内で確定する。

この設計により、将来の人対人化でも二重送信・古い画面からの操作を防止できる。

## 7. データモデル

既存の Better Auth `user` テーブルは変更せず、ゲーム固有テーブルを追加する。

### 7.1 `game_match`

| 列 | 型・例 | 説明 |
| --- | --- | --- |
| `id` | text / UUID | マッチ ID |
| `status` | `active`, `completed`, `abandoned` | マッチ状態 |
| `mode` | `cpu` | 対戦モード。将来 `pvp` を追加 |
| `turnSide` | `human`, `cpu` | 現在の手番 |
| `turnNumber` | integer | 手数。人間ターン開始ごとに増加 |
| `mapKey` | text | 固定マップ識別子 |
| `mapSeed` | integer nullable | 将来のランダムマップ再現用 |
| `version` | integer | 楽観的排他制御用の版数 |
| `winnerSide` | nullable enum | 勝者 |
| `finishReason` | nullable enum | `planet_destroyed`, `surrender` など |
| `createdAt` / `updatedAt` / `finishedAt` | timestamp | 監査・履歴用時刻 |

### 7.2 `game_participant`

| 列 | 説明 |
| --- | --- |
| `id` | 参加者 ID |
| `matchId` | 所属マッチ |
| `side` | `human` または `cpu`。マッチ内で一意 |
| `userId` | 人間陣営のみ既存 `user.id` を設定 |
| `planetX` / `planetY` / `planetHp` | 主惑星の位置と現在 HP |
| `createdAt` / `updatedAt` | 監査用時刻 |

### 7.3 `game_unit`

| 列 | 説明 |
| --- | --- |
| `id` | ユニット ID |
| `matchId` / `participantId` | 所属先 |
| `kind` | `battleship` または `fighter` |
| `x` / `y` | 現在座標 |
| `hp` | 現在 HP |
| `isDestroyed` | 撃破済みフラグ。履歴再生のため物理削除しない |
| `hasActed` | 現在ターンで行動済みか |
| `createdAt` / `updatedAt` | 監査用時刻 |

性能値はマスターテーブルではなく、まずドメイン層の型付き定数として定義する。編成・成長要素を実装する段階でマスター化する。

### 7.4 `game_action`

| 列 | 説明 |
| --- | --- |
| `id` | アクション ID |
| `matchId` / `actorUnitId` | マッチと実行ユニット |
| `turnNumber` / `side` | 実行時のターン・陣営 |
| `kind` | `move`, `attack`, `wait`, `end_turn`, `surrender` |
| `payload` | 実行内容 JSON。移動先、対象、乱数値、命中結果、ダメージなど |
| `createdAt` | 実行日時 |

攻撃では判定前後の HP、命中率、乱数値、結果、ダメージを `payload` に保存する。これにより不具合調査や将来のリプレイ実装を可能にする。

### 7.5 整合性制約とインデックス

- `game_participant`: `(match_id, side)` にユニーク制約。
- `game_unit`: `(match_id, x, y)` は生存ユニットのみ一意である必要があるため、アプリケーション層で検証する。
- `game_action`: `(match_id, created_at)` と `(match_id, turn_number)` の検索用インデックスを作成する。
- API は、ログインユーザーが人間陣営として所属するマッチだけを読み書き可能とする。

## 8. API 仕様

ORPC の `game` ルーターを追加する。すべてのゲーム API は認証必須とする。

| 手続き | 入力 | 出力 | 主な検証 |
| --- | --- | --- | --- |
| `game.createCpuMatch` | `mapKey?` | 新規マッチのスナップショット | 進行中マッチ数の上限、マップ存在 |
| `game.listMatches` | `status?`, `cursor?` | マッチ一覧と次カーソル | 自分が参加者であること |
| `game.getMatch` | `matchId` | マップ・参加者・生存ユニット・直近履歴・操作可否 | 所有者確認 |
| `game.submitAction` | `matchId`, `expectedVersion`, `action` | 更新後スナップショット、攻撃結果 | 手番、所有者、未行動、経路、射線、対象、版数 |
| `game.surrender` | `matchId`, `expectedVersion` | 完了後スナップショット | アクティブな自分のマッチ |

`action` は判別可能なユニオンとする。

- `move`: `{ type: "move", unitId, destination: { x, y } }`
- `attack`: `{ type: "attack", unitId, target: { type: "unit" | "planet", id? } }`
- `wait`: `{ type: "wait", unitId }`
- `endTurn`: `{ type: "endTurn" }`

攻撃成功レスポンスには、攻撃演出で必要な `attackResult` を含める。クライアントは表示用の再計算を行わない。

## 9. エラー仕様

| コード | 発生条件 | UI の扱い |
| --- | --- | --- |
| `MATCH_NOT_FOUND` | マッチが存在しない | ダッシュボードへ戻り通知 |
| `MATCH_FORBIDDEN` | 所有者でないマッチの操作 | エラー通知、状態を表示しない |
| `MATCH_FINISHED` | 終了済みマッチを操作 | 結果表示へ遷移 |
| `STALE_MATCH_VERSION` | 画面上の状態が古い | 自動再取得後、再操作を案内 |
| `NOT_YOUR_TURN` | CPU ターン中など | 状態を再取得 |
| `INVALID_ACTION` | 行動済み・対象不正・範囲外 | 理由を表示し、選択状態を維持 |
| `INVALID_PATH` | 障害物で経路が存在しない | 移動候補を再描画 |
| `TARGET_OUT_OF_RANGE` | 射程外または射線遮断 | 攻撃候補を再描画 |

内部エラーの詳細、乱数シード、他ユーザーの情報はクライアントへ返さない。

## 10. 実装計画

各フェーズの完了時に、該当範囲の Bun テスト、型検査、Biome チェックを実行する。変更が DB スキーマを含む場合は Drizzle のマイグレーションを生成し、手編集しない。

### フェーズ 0: 仕様確定と技術基盤

**目的:** 実装可能な型と境界を固定する。

- ドメインモデル、列挙値、座標・スナップショット DTO を定義する。
- 固定マップの地形・初期配置を型付き定数として定義する。
- 既存 `phaser-game.tsx` の試作表示を、ゲーム画面へ置き換えるためのコンポーネント構成に分解する。
- ルート、API、DB スキーマの命名規則を確認する。

**完了条件:** 画面と API が共有するゲーム型の責務が明確で、固定マップをコード上で検証できる。

### フェーズ 1: ドメインゲームエンジン

**目的:** UI や DB に依存しない、検証可能なゲームルールを実装する。

- グリッド座標、占有判定、幅優先探索による移動経路探索を実装する。
- 射程・射線・攻撃対象の検証を実装する。
- 命中・クリティカル・ダメージ・撃破・勝敗判定を実装する。
- ターン開始、行動済み管理、ターン終了を実装する。
- 注入可能な乱数生成器と決定的な CPU 方針を実装する。

**テスト:**

- 障害物を迂回する移動、移動不可、他ユニット占有を検証する。
- 射程外・遮蔽・味方対象・撃破済み対象が拒否されることを検証する。
- `miss` / `hit` / `critical` の境界値とダメージを検証する。
- 主惑星撃破時に即時終了することを検証する。
- CPU が優先順位に従うことを検証する。

**完了条件:** ルールの主要分岐が単体テストで網羅され、同じ初期状態と乱数入力から同じ結果が得られる。

### フェーズ 2: 永続化とゲーム API

**目的:** 認証ユーザーの対局を安全に作成・保存・再開できるようにする。

- `game_match`、`game_participant`、`game_unit`、`game_action` の Drizzle スキーマとリレーションを追加する。
- マイグレーションを `drizzle-kit generate` で生成する。
- マッチ作成、一覧、詳細取得、アクション送信、降参の ORPC 手続きを実装する。
- 1 操作につきマッチ、ユニット、履歴、バージョンを整合的に更新する。
- CPU ターンをサーバー側で処理し、確定後の状態のみ返す。

**テスト:**

- 未認証アクセス拒否、他人のマッチ操作拒否、入力スキーマ検証を行う。
- 二重送信と `expectedVersion` 不一致を検証する。
- マッチ作成から終了までの API 結合テストを行う。

**完了条件:** ページ再読み込み後も同一マッチを再開でき、不正な操作で状態が変化しない。

### フェーズ 3: 対局 UI と Phaser 描画

**目的:** 人間がゲーム状態を理解し、合法手を選択できる UI を提供する。

- 認証配下にマッチ画面ルートを追加する。
- ダッシュボードに「CPU 戦を開始」「進行中の対局を再開」「履歴を見る」を追加する。
- Phaser シーンでグリッド、小惑星、惑星、各ユニットを描画する。
- React UI と Phaser イベントを接続し、選択、候補表示、移動、攻撃、待機、ターン終了を実装する。
- API 送信中・CPU 行動中・競合エラー時の表示を実装する。

**テスト:**

- 表示テキスト、操作パネルの活性 / 非活性、API 呼び出しパラメーターをテストする。
- Phaser 描画に渡すスナップショット変換をテストする。
- 小さい画面で主要操作が隠れないことをブラウザで確認する。

**完了条件:** 新規ゲーム開始から、移動・攻撃・CPU 応答・勝敗表示までをブラウザ上で連続して操作できる。

### フェーズ 4: 攻撃演出と品質向上

**目的:** 攻撃結果を分かりやすく、ゲームの魅力として伝える。

- 攻撃時に専用演出ウィンドウを開き、攻撃結果を安全に送信する。
- ポップアップ拒否時のモーダルフォールバックを実装する。
- `miss`、`hit`、`critical` の Phaser 演出とスキップ操作を実装する。
- 結果反映後に対局状態を再取得し、表示の不整合を防止する。
- キーボード操作、`prefers-reduced-motion`、エラー通知を整備する。

**テスト:**

- 演出データの変換と結果別表示をテストする。
- ポップアップ失敗時にモーダルへ切り替わることをテストする。
- 演出が状態更新を二重実行しないことを結合テストする。

**完了条件:** すべての攻撃結果が区別可能で、演出失敗・スキップ時もゲームを継続できる。

### フェーズ 5: バランス・リリース検証

**目的:** MVP を安定して利用できる状態にする。

- 自動シミュレーションで CPU 対 CPU の多数対局を実施し、無限ターン・到達不能・極端な勝率を検知する。
- 戦闘ログを確認し、初期パラメーターを調整する。
- 新規開始、再開、降参、勝利、敗北、通信失敗、競合の受け入れテストを実施する。
- 型検査、Biome、ユニットテストを CI で必須化する。

**完了条件:** 既知の重大不具合がなく、主要フローの自動テストが継続実行される。

## 11. テスト戦略

| テスト層 | 対象 | 重点 |
| --- | --- | --- |
| ユニットテスト | ドメインルール、座標、乱数、CPU | 境界値、再現性、不正手拒否 |
| API 結合テスト | ORPC、認可、DB 更新 | トランザクション、競合、再開 |
| コンポーネントテスト | 操作パネル、状態表示、演出フォールバック | ユーザー操作とエラー表示 |
| E2E / 手動受入 | ブラウザ全体 | 対局開始から勝敗、レスポンシブ、ポップアップ |
| シミュレーション | CPU 対 CPU | バランス、停止性、例外の検出 |

ゲームロジックのテストでは、乱数を固定値列として注入する。確率分布そのものの統計テストではなく、閾値と判定分岐を決定的に検証する。

## 12. 受け入れ基準

MVP は次をすべて満たした時点で完了とする。

1. 認証済みユーザーがダッシュボードから CPU 戦を開始できる。
2. 盤面に主惑星、小惑星、戦艦、戦闘機がルールどおりに表示される。
3. ユーザーは合法な移動・攻撃・待機・ターン終了のみを実行できる。
4. 小惑星・ユニット・惑星を通過する移動、射線が遮られた攻撃、範囲外攻撃は拒否される。
5. 攻撃ごとに `miss`、`hit`、`critical` のいずれかが記録され、ダメージと HP が正しく反映される。
6. 攻撃演出は別ウィンドウで再生され、ブロック時にはモーダルで再生される。
7. CPU が人間ターン終了後に合法手だけを実行する。
8. 敵主惑星の HP が 0 以下になると勝敗が確定し、追加行動は受け付けない。
9. 進行中の対局は再読み込み後に再開でき、履歴から終了済み対局を確認できる。
10. ルール、API 認可、主要 UI 操作を対象とした自動テストが通過する。

## 13. 将来拡張の方針

### 人対人対戦

`mode` に `pvp`、参加者に第 2 ユーザーを追加し、現在の `expectedVersion` による楽観的排他制御を維持する。最初は非同期ターン制（相手の操作後に状態を再取得）として実装し、その後に WebSocket または Server-Sent Events により更新通知を追加する。

### コンテンツ拡張

- マップ定義を JSON または DB マスターに分離し、複数マップとランダム生成を追加する。
- ユニット性能をマスター化し、巡洋艦・支援艦・防衛施設などを追加する。
- 地形効果、視界、スキル、範囲攻撃は、ドメイン層の行動ユニオンを拡張して導入する。
- `game_action` の履歴を利用し、リプレイ・対戦分析・ランキングを追加する。

6. 将来の人対人対戦で必要となる通知、制限時間、不正行為対策の優先度。
